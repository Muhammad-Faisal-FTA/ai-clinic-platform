1. Purpose

This TRD defines the functional and non-functional requirements for the AI Clinic Platform's initial buildable scope: patient booking via a conversational Receptionist Agent, doctor/admin management surfaces, and the supporting auth, notification, and audit systems. Every requirement carries an ID intended for direct reference in code comments, commit messages, and PR descriptions — e.g. // Implements FR-APT-003.

2. System overview

Two deployables: apps/web (Next.js — UI, auth, business logic) and apps/agent-service (Node.js — LangChain.js/LangGraph.js agents on Gemini). Full architectural detail lives in the companion Architecture Analysis Report and Folder Structure Guide; this TRD assumes that structure and does not repeat it.

Confirmed technology decision: database is PostgreSQL, not MongoDB. This was already the working assumption throughout this TRD (§7 data model is relational, FR-APT-002's double-booking prevention relies on a relational unique constraint, and shared agent memory uses the pgvector extension on the same database rather than a separate vector store — see Architecture Analysis Report §5). One database system to run, not two.

4.9 Payment — FR-PAY

Scope note: this is minimal consultation-fee collection at booking time, not the full Billing Service (invoicing, insurance claims, refund automation) from the original architecture doc — that remains deferred to Phase 2–3. Recommended method: Stripe Checkout — free to integrate (no setup fee, no monthly fee, pay only ~2.9% + 30¢ per successful transaction), ships a free sandbox/test mode, and uses a Stripe-hosted payment page so the platform never touches raw card data. If your target market is a region Stripe doesn't serve directly (e.g. Pakistan), swap in a local aggregator (PayFast, JazzCash, or EasyPaisa merchant API) behind the same PaymentProvider interface — the requirements below don't change either way.

IDRequirementPriorityPhase
FR-PAY-001The system shall collect a consultation fee from the patient at the point of booking confirmation, before the appointment is marked confirmed.M1
FR-PAY-002The system shall redirect the patient to a hosted checkout page (Stripe Checkout or equivalent) rather than collecting card details on any first-party form.M1
FR-PAY-003The system shall mark an appointment as confirmed only after receiving a successful payment webhook, not on client-side redirect alone.M1
FR-PAY-004The system shall record every payment attempt (succeeded, failed, refunded) with amount, currency, and provider transaction ID.M1
FR-PAY-005The system shall support a free "pay at clinic" fallback option alongside online payment, so a failed/unavailable payment integration never blocks booking entirely.S1
FR-PAY-006The system shall allow an admin to issue a refund through the provider's API, logged the same way as any other payment event.C2
Acceptance (FR-PAY-003): a patient who closes the browser tab immediately after paying, before the redirect completes, still ends up with a confirmed appointment — because confirmation is driven by the provider's server-to-server webhook, not the client returning to your site.

5. Non-functional requirements

5.1 Security — NFR-SEC

IDRequirementPriority
NFR-SEC-001All patient data shall be encrypted in transit (TLS 1.2+) for every network hop, including internal service-to-service calls.M
NFR-SEC-002Passwords shall be hashed with bcrypt (cost factor ≥ 12), never stored or logged in plaintext.M
NFR-SEC-003The apps/agent-service process shall not hold a database connection string or direct DB credentials under any configuration.M
NFR-SEC-004All internal API calls between apps/web and apps/agent-service shall be authenticated via a shared service token.M
NFR-SEC-005No real patient identifiers or medical details shall be transmitted to the Gemini free-tier API; synthetic data only until paid tier/Vertex AI is in place.M
NFR-SEC-006The platform shall never store or process raw card numbers — all card data stays within the payment provider's hosted checkout (PCI SAQ-A scope only).M

9. Sample acceptance criteria (end-to-end)

FEAT-005 — Conversational appointment booking

Given a logged-in patient with ROLE-PATIENT, when they message "I need to see a dermatologist this week," then the agent shall: retrieve dermatology-specialty doctors (FR-AGT-002) → propose an available slot → wait for explicit patient confirmation (FR-AGT-004) → call bookAppointment.tool.ts → receive a confirmed Appointment record → log the full exchange to the audit log (FR-AGT-008) → trigger AppointmentCreated → patient receives an email confirmation (FR-NOT-001) — and the doctor's calendar reflects the new appointment without a double-booking (FR-APT-002).

10. Out of scope (Phase 2–3 — reference only)

Full Billing Service (invoicing, multi-line receipts, insurance claims, automated refund workflows), Insurance Service + Insurance Agent, Medical Record Service + Doctor Copilot, Prescription Service, Queue Service + Queue Agent, Analytics Service + Analytics Agent, Search Service, Document Service, Marketing Agent, Follow-up Agent, WhatsApp/Voice interfaces, Public API, multi-tenant support. Rationale for each deferral is documented in the Architecture Analysis Report, §6.

Minimal consultation-fee payment collection (FR-PAY-*, FEAT-015) is not deferred — it's now in Phase 1, scoped narrowly to "collect one fee via a hosted checkout page," distinct from the full Billing Service above.

Note on FR-APT-005: manual booking form is intentionally deferred to Phase 1 (FEAT-013) so Phase 0 forces every booking through the agent path — a deliberate scoping choice to prove the conversational flow works before adding a parallel path that could mask agent bugs.
